# 백엔드 구현 체크리스트

2026년 11월 20일 팀 회의 변경 사항과 현재 구현 상태를 기준으로 정리한 체크리스트다. 체크된 항목은 현재 저장소에 구현·검증된 기능이며, 소식지·요청문·업체 검색·채팅 모바일 화면, 실제 모델 기반 사진 분석·진단 재생성, 실제 업체 데이터, 회원가입 화면·4개 탭은 후속 구현 대상이다. WebSocket 실시간 채팅과 방별 미읽음 수는 백엔드에 구현했다. 실제 Supabase·모바일·외부 모델·보조금24 운영 키를 함께 연결한 검증은 별도 항목으로 관리한다.

현재 코드에는 DB·인증·기록 CRUD(`material` 포함), **입력값 기반 샘플 일괄 분석(`POST /records/{record_id}/analyze`)**, 사진·입력·결과 화면, **회원 프로필 API(`GET/PUT /me/profile`)·지역 목록(`GET /regions`)·내 기록 목록(`GET /records`)**, 모바일 프로필·기록 화면, **소식지 백엔드(목록·상세·검증 시드·보조금24 수동 동기화)**, **요청문 생성·기본 양식(LLM 연동, 실패 시 502/503/504)**, **작업 종류·업체 검색**, **요청인–업체 1:1 채팅 REST·WebSocket·방별 미읽음 수**, 그리고 **레거시/보류 상태인 AI 추가 질문 대화 API(`messages`, `next-question`)**가 구현되어 있다. 다음 핵심 작업은 새 기능의 모바일 화면 연결, 실제 사진/LLM 기반 진단, 실제 업체·계정 데이터 준비, 모바일 채팅 화면의 WebSocket·읽음 호출 연결이다.

## 회원·인증

회원 인증은 Supabase Auth(이메일·비밀번호)가 담당한다. 모바일 앱은 Supabase에 로그인하고 FastAPI는 전달받은 액세스 토큰으로 사용자와 리소스 소유권을 확인한다. 일반 회원가입은 `요청인` 전용이며 `닉네임`, `ID(이메일)`, `PW`, `거주 지역`(필수), `등록 주소`(선택), `거주 형태`(`월세`, `전세`, `반전세`, `자가`, `기타`)를 입력받는다. 시연용 `업체` 계정은 사전 등록한다. 비밀번호 재설정은 후속 범위다. [기존 결정](PROJECT_PLAN.md#합의한-범위)

## 하자 일괄 분석 및 진단 (2단계 구현 완료)

분석 페이지에서 채팅 없이 사진(1~2장) + 위치 + 재질(+ 선택 증상 메모)을 한 번에 받는다. 사진 관찰(YOLO·SAM·비전 LLM 보조)과 텍스트 구조화 진단을 분리해 구현했고, 두 모델 경로가 모두 미설정일 때만 샘플 결과를 저장한다.

- [x] `POST /records/{record_id}/analyze` (multipart) — 사진 1~2장(전체·근접, 1장 필수)과 위치·재질·선택 증상 메모, 외부 분석 동의 여부 일괄 처리
- [x] 업로드 파일 형식(JPEG/PNG/HEIC/HEIF, magic byte)·크기(10MB)·사진 수·역할 검증과 소유권 확인
- [x] 서버 로컬 YOLO 탐지와 라벨 한국어 정규화(`label`), 원본 클래스명 보존(`raw_label`), class별 신뢰도·bbox·`area_ratio`
- [x] YOLO 미탐지·실행 불가 사진만 비전 LLM 독립 관찰(긴 변 1280px JPEG, 좌표 미생성)
- [x] 사진별 `status`(`not_analyzed`/`analyzed`/`failed`), `source`(`sample`/`yolo`/`yolo_sam`/`vision_llm`), `vision_observation`, 마스크 기반 `area_ratio` 반환
- [x] 샘플 모드에서 사진을 실제 분석한 것처럼 표현하지 않고 `applied=false`, `source=sample`, 샘플 안내 반환
- [x] 입력한 위치·재질·증상으로 결정적 샘플 진단 생성
- [x] 관찰 상태·탐지·마스크·신뢰도를 DB에 저장하고 원본 사진은 저장하지 않는 처리
- [x] 업로드 임시 파일의 성공·실패 시 닫기(원본 미저장)와 외부 분석 동의 값 검증 *(샘플은 외부 호출 없음)*
- [x] 구조화 진단 응답 검증·JSONB 저장(모델 생성 시 `source=llm`, 샘플은 `sample`):
  - `observations` (샘플은 입력 기반 관찰 요약)
  - `severity_score` (`0~100` 정수), `severity_level` (`low`/`medium`/`high`/`undetermined`), `reason` (산정 근거)
  - `causes` (추정 원인), `estimation_notice` (AI 추정 안내 문구), `unknowns` (미확인 정보)
  - `recommended_action` (`self_care`/`inspection`/`provider_consult`), `care_steps`, `supplies` (해결방안 통합)
  - `prevention_tips` (재발 방지책)
  - `work_type_id`(DB 일치 시 저장, 미일치·판단 보류·복합 원인은 `원인 점검`), `work_type_reason` (추천 작업·이유)
  - `source` (`llm`/`sample`)
- [x] 입력 스냅샷 생성, 저장 직전 `input_revision` 재확인, 동시 분석·입력 변경 시 409와 부분 저장 방지
- [x] `POST /records/{record_id}/diagnosis?regenerate=true` — 모델 기반 진단 재생성, 입력 버전 일치 시 재사용, 생성 중 입력 변경 409

- [x] 입력 버전·진단 생성 번호가 모두 맞는 요청문만 재사용
- [x] 생성 도중 입력(`revision_conflict`) 또는 진단(`diagnosis_conflict`)이 바뀌면 저장 없이 `409`
- [x] `?regenerate=true` 명시적 재생성과 생성 실패 시 기존 값 유지
- [x] `GET /records/{record_id}/drafts/{kind}/template` — 모델 호출 없는 기본 양식(진단 없어도 `200`)
- [x] 모델 키 미설정 `503`, 호출·응답 오류 `502`, 제한 시간 초과 `504`. 샘플 결과를 생성 결과로 대체하지 않음
- [x] 외부 모델에 프로필 닉네임·등록 주소·거주 형태·이메일을 보내지 않고, 증상 메모의 이메일·휴대전화 번호를 전송 전에 제거
- [x] 프롬프트·모델 응답·요청 본문·개인정보를 로그에 남기지 않음
- [x] 요청문 편집본 저장 API를 추가하지 않음
- [ ] *(모바일 범위)* `자가` 요청인 임대인 요청문 기본 숨김, 견적 요청문의 채팅 초안·복사

요청문 생성은 서버의 단일 LLM 제공사(OpenAI 호환 Chat Completions, `app/llm.py`)를 사용한다. 실제 키·네트워크 호출은 이번 환경에서 검증하지 않았고 테스트는 고정 응답으로 대체한다.

현재 프롬프트에는 `symptoms` 원문이 포함되고 이메일·휴대전화만 마스킹한다. 증상 메모를 외부 모델 입력으로 계속 사용할지, 사용 시 동의·고지·저장 방식을 정하는 것은 **팀 회의 전**이며, 결정 전 구현은 유지한다. 실제 사용자 데이터 대신 가상 데이터 또는 자체 호스팅 모델로 시연한다.

- [x] DB 조회 오류와 빈 검색 결과 구분(`500`)
- [x] 공개 연락처와 별도로 앱 내 채팅 가능 여부(`chat_available`) 구분

현재 업체 관련 테이블(`providers`, `regions`, `work_types`, `provider_regions`, `provider_work_types`)과 검색 API는 준비되어 있다. 실제 업체·계정 데이터는 확인된 자료가 없어 시드하지 않았고, 샘플 검색 흐름만 완성했다.

## 11월 21일 시안 검토 후속 작업

이메일·비밀번호 인증을 유지하고 프로필 사진은 제외한다. 소셜 로그인은 시간이 남으면 재검토한다.

- [ ] 진단 신뢰도 정의·산정 근거·검증·필드 계약 확정 후 필드 추가 (정의 대기, 이번 구현 제외)
- [x] WebSocket 실시간 채팅 (`WS /chat/ws`, 인증·`ready`/`message` 이벤트·재연결은 REST 이력 동기화)
- [x] 채팅방별 미읽음 수 저장·조회·읽음 갱신 (`011`, `GET /chat/rooms.unread_count`, `POST /chat/rooms/{room_id}/read`)

읽음 시점은 앱이 채팅방에 들어가 메시지 이력을 받은 직후로 정했다. 서버가 읽음 시각을 저장하므로 같은 계정의 다른 기기도 공유하며, 본인이 보낸 메시지는 미읽음으로 세지 않는다.

비회원 전체 소식·업체 열람안, “분석을 해야 등록되는 흐름”의 대상·시점, 발생/발견일 입력은 검토 중이다. 사진 보관은 비공개 Storage+Signed URL로, 추천 작업 연결은 DB 작업 종류 매칭과 `원인 점검` 폴백으로 확정했다([ADR 0002](../adr/0002-private-storage-for-defect-photos.md)). 견적 요청서·제안서·수락, 소식지 페이지네이션·주기 동기화, 업체 평점·상세는 확정 설계이며 코드는 아직 없다. 근거와 선택지는 [프로젝트 계획의 시안 검토](PROJECT_PLAN.md#11월-21일-프론트-시안-검토)를 따른다.
