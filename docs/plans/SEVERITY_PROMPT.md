# severity_score 프롬프트 개정안 (균열 / 벗겨짐 / 곰팡이)

작성 2026-11-22 · 대상 코드: `apps/api/app/diagnosis.py` 41–51행(`SYSTEM_PROMPT`), 53–84행(`PROMPT_TEMPLATE`)
정본 루브릭: `docs/plans/SEVERITY_RUBRIC.md` §16 (프로파일 표), §6 (산식·가중치), §4 (트랙)
**이 문서는 코드를 수정하지 않았다.** 아래 두 블록을 그대로 붙이면 된다(§8).

---

## 1. 이 프롬프트가 하는 일 (5줄)

1. **심각도 산출 규칙을 처음으로 프롬프트에 넣는다.** 현재 프롬프트에는 `severity_score`의 "0~100 정수"라는 형식 제약만 있고, **어떤 신호를 몇 점으로 볼지에 대한 지침이 전혀 없다**(`diagnosis.py:46`). 그래서 같은 사진에서도 모델이 임의로 30·55·70을 고른다.
2. **계산을 시키지 않고 표에서 고르게 한다.** 가중치 16~18개, floor·cap 표 12개를 문장으로 주면 모델은 **순서를 틀린다**(floor를 cap 뒤에 적용해 69가 70 high가 되는 사례). 그래서 루브릭 §6의 산식으로 미리 계산한 **22행 표(§16-2)** 만 주고 "한 행을 골라 그대로 쓰라"고 지시한다.
3. **없는 값을 만들지 않게 막는다.** 사진에는 균열폭(mm)·절대면적(㎡)·공기 중 농도(CFU/㎥)·부착강도(MPa)가 없다. 프롬프트에 기준 수치나 표준번호를 넣으면 모델이 그 숫자를 **측정값처럼** 인용하므로, 프롬프트 본문에는 숫자 기준값·조문·표준번호를 **하나도 넣지 않는다**.
4. **안전 측으로 기울인다.** 근거가 얕으면 점수는 자동으로 낮아진다(판독 품질 55 상한, 화면 점유 비율 60 상한, 메모 가점 25 상한). 네 경우에는 점수를 아예 만들지 않고 `null`로 둔다.
5. **응답이 깨져 502가 나는 경로를 막는다.** 키 13개 전부, 배열 누락 금지, `severity_score`는 따옴표 없는 정수 하나, `severity_level` 키 생성 금지. 현재 서버는 배열 하나만 빠져도 **진단 전체를 실패(502)** 로 처리한다(`_text`·`_text_list`).

## 2. severity_score 산정 절차 (모델이 따를 순서)

| 단계 | 하는 일 | 담당 | 근거 |
|---|---|---|---|
| 1. **신호 수집** | 사진 관찰·사용자 입력에서 **실제로 확인되는 것만** 신호로 나열한다 | 모델 | 루브릭 §4-2 |
| 2. **트랙 확인** | 그 사진에 탐지 결과가 왔는지(D) 관찰 요약이 왔는지(V) 구분한다. 한 사진에 둘 다 오지 않는다 | 모델 | 루브릭 §4-1 |
| 3. **항목 선택** | 유형을 정하고, 확인된 신뢰도 40% 미만 탐지·상한 규칙을 먼저 적용한다 | 모델 | SYSTEM [2]·[4] |
| 4. **표 lookup** | 22행 중 가장 가까운 행 **하나**를 고른다. 여러 행이 맞으면 **가장 큰 점수**, 합산 없음 | 모델 | 루브릭 §16-2 |
| 5. **합산** | **하지 않는다.** 표 값이 곧 최종 후보이며, 가중치 합산은 표를 만들 때 이미 반영됐다 | — (문서) | 루브릭 §16-3 |
| 6. **clamp** | **모델은 하지 않는다.** 0~100 범위·정수 여부·`null` 허용은 **서버가 검증**하고 벗어나면 502 | 서버 | `diagnosis.py:194-200` |
| 7. **floor / cap** | 표의 행에 이미 반영돼 있다(예: "탈락해서 바탕이 드러남 = 70"). 모델은 행만 고른다 | 문서 | 루브릭 §6-1~6-3 |
| 8. **밴드** | 40/70 경계는 **서버가 점수로 재계산**한다. 모델은 `severity_level`을 출력하지 않는다 | 서버 | `diagnosis.py:203-208` |
| 9. **action** | 밴드 → action 매핑 후, 상향 조건(철근 노출·진행성+구조부·탈락·누수 이력+현재 젖음)이면 한 단계 올린다 | 모델 | SYSTEM [7] |

> **왜 합산을 없앴나**: 가중치를 더하게 하면 (a) 순서 오류, (b) `84.0`·`"84"`·`true` 같은 타입 오류(모두 502), (c) 39↔40·69↔70 경계 흔들림이 동시에 생긴다. 표 선택은 실패 모드를 "행 하나 잘못 고르기"로 줄인다.

## 3. SYSTEM_PROMPT 개정안

`apps/api/app/diagnosis.py` 41–51행을 아래 블록으로 교체한다. **38줄**(목표 40줄 이내), 약 1.1K 토큰.

```python
SYSTEM_PROMPT = """\
너는 임차 주택 하자 기록을 정리해 "AI 추정 진단"을 만드는 도우미다. 아래 순서를 지키고, 규칙에 없는 내용은 만들지 않는다.

[1] 신호를 먼저 모은다
사진 관찰과 사용자 입력에서 실제로 확인되는 것만 신호로 세운다. 사진에 없으면 없는 것이다. 일반 상식이나 기억으로 신호를 보태지 않는다.
사진은 두 종류로 온다. 탐지 결과(라벨·신뢰도·화면 점유 비율)가 오는 사진과, 관찰 요약(서술)이 오는 사진이다. 한 사진에 둘 다 오지는 않는다.

[2] 유형을 고른다
suspected_types에는 "균열", "벗겨짐", "곰팡이"만 넣는다. 맞는 것이 없으면 []로 둔다. 점수를 매기려면 이 셋 중 최소 하나를 반드시 넣는다.

[3] 점수는 표에서 고른다
점수표에서 지금 신호와 가장 가까운 행 하나를 골라 그 점수를 그대로 쓴다. 더하거나 빼지 않고, 표에 없는 값을 만들지 않는다.
두 행이 함께 맞으면 큰 점수를 쓴다. 정확히 맞는 행이 없으면 가장 가까운 행을 쓰고 그 사실을 reason에 한 문장 쓴다.

[4] 상한을 표보다 먼저 적용한다
- "상태: failed" 또는 "판독 불가:" 줄이 실제로 있을 때만 판독 품질 저하로 보고, 점수는 55를 넘지 않는다. 선명한 사진을 흐리다고 쓰지 않는다.
- 화면 점유 비율은 상한값이므로 그것만으로 60을 넘지 않는다. 증상 메모에서 온 가점은 합계 25점을 넘지 않는다. 단 메모에 측정 사실과 수치가 함께 적힌 경우는 표의 "사용자가 직접 재서 폭을 수치로 밝힘" 행을 그대로 쓰고, 이 값은 가산이 아니므로 25점 상한을 받지 않는다. 탐지 신뢰도가 40% 미만인 항목은 신호로 세지 않는다.
- 사진 근거 없이 메모만 있으면 점수는 55를 넘지 않고 recommended_action은 inspection 이상이다. 단 메모에 측정 사실과 수치가 함께 적힌 경우는 이 상한을 풀고 표의 해당 행을 그대로 쓴다.

[5] 보류는 정상이다
다음 네 경우에만 severity_score를 null로 둔다. ①모든 사진이 판독 불가이고 메모에도 확인 가능한 진술이 없다 ②먼지·그을음·도장 변색과 구별되지 않는다 ③두 사진이 서로 다른 유형을 지목해 하나로 정할 수 없다 ④안전한지 묻는 것뿐이다.
null이면 suspected_types는 []이고 recommended_action은 inspection 또는 provider_consult다.

[6] 유형이 2개 이상이면
점수는 유형별로 따로 골라 높은 쪽을 쓰고, recommended_action은 그중 가장 강한 것을 쓴다. work_type_name은 "원인 점검"으로 쓰고, reason에 "원인이 복합적이어서 원인 점검을 함께 권장합니다"를 넣는다.

[7] 밴드와 행동
0~39 self_care, 40~69 inspection, 70~100 provider_consult.
점수가 69 이하여도 철근 노출·녹물 / 구조부나 천장에서 점점 벌어지거나 넓어짐 / 탈락해서 바탕이 드러남 / 누수 이력이 있고 지금도 젖어 있음 이면 recommended_action을 provider_consult로 올린다.

[8] 하지 말 것
폭·면적·농도 같은 측정값을 새로 만들지 않는다. 사진으로는 잴 수 없다.
법령·조문·표준번호·기준 수치를 인용하지 않는다. "하자입니다", "결로가 원인입니다"처럼 단정하지 않고 "가능성", "확인 필요"로 쓴다.
금액·업체명·일정·공사기간을 만들지 않는다. 곰팡이 종(屬·種)을 식별하지 않는다. 건물 연식·경과년수를 추정하지 않는다. 점수를 퍼센트·확률로 쓰지 않는다.

[9] 출력 규칙
severity_score는 정수 하나 또는 null이다. 소수점·따옴표·true/false를 쓰지 않고 100을 넘으면 100으로 쓴다. severity_level 키를 만들지 않는다. 단계는 서버가 점수로 계산한다.
JSON의 키 13개를 모두 쓰고, 값이 없으면 빈 배열 []을 쓴다. observations와 reason은 빈 문자열로 두지 않는다.
work_type_id는 항상 null로 두고 work_type_name에 등록된 이름을 쓴다. 각 배열은 3개 이하, 각 항목은 한 문장으로 쓴다.
"""
```

> **주의 3 (실측 예외)**: `[4]`의 "메모 가점 25점 상한"과 "사진 없이 55 상한"에는 **사용자가 직접 잰 값**만 예외다.
> 루브릭 §8-3이 "실측값 입력 → 상한 해제"를 규정하고 §12 C-8의 기대값이 `70`이므로, 두 상한을 그대로 두면
> C13 경로(텍스트만으로 `high`에 도달하는 유일한 경로)가 죽고 self-check와 어긋난다.
> 예외는 **측정 주체가 사람이고 수치가 함께 적힌 경우**로만 한정한다. "많이 벌어졌다" 같은 서술은 예외가 아니다.

### 4-1. 플레이스홀더 5개 (전부 유지 — `build_prompt` 무변경)

| 플레이스홀더 | 채우는 코드 | 주의 |
|---|---|---|
| `{location}` | `_redact(record["location"])` | 개인정보 마스킹 유지. `/analyze`·`/diagnosis` 모두 필수 입력이므로 항상 값이 있다 |
| `{material}` | `_redact(record["material"])` | 〃 |
| `{symptoms}` | `_redact(symptoms)` 또는 `"미입력"` | 〃. 빈 문자열이 아니라 `미입력`으로 치환된다 |
| `{photos}` | `_photo_lines(...)` | `role`·`status`·탐지 라벨/신뢰도/점유 비율·관찰 요약·판독 불가 사유 |

| `{` `}` (JSON 블록) | — | **`{{` `}}`로 이중 이스케이프해야 한다.** `str.format`이 단일 중괄호를 필드로 해석해 `KeyError`를 낸다 |

> **주의 2**: `test_prompt_uses_only_observations_and_masks_contact_details`가 프롬프트 전문에서 **3자리 금지 문자열**(`911`·`922`·`933`·`944`)과 `SECRET-` 부재를 검사한다(`test_diagnosis.py:189-197`). 새 블록에 그 조합이 없음을 교체 후 확인한다.

## 5. 계산 예시 3개 (입력 → 항목 점수 → 합계 → band → action)

공통: 사진 1장은 **탐지(D)** 또는 **관찰(V)** 중 하나만 준다. 아래 `합계`는 루브릭 §6 산식으로 검산한 값이고, 모델은 §16-2 표에서 같은 값을 고른다.

## 6. 판단 보류 조건과 그 출력 형태

### 6-1. `null`을 쓰는 4가지 (그 외에는 쓰지 않는다)

| # | 조건 | 판별 방법 |
|---|---|---|
| ① | 모든 사진이 `상태: failed`/`판독 불가:` **이고** 메모에도 확인 가능한 진술이 없다 | `_photo_lines`의 `상태`·`판독 불가` 줄 + `증상 메모: 미입력` |
| ② | 먼지·그을음·도장 변색과 구별되지 않는다 | 관찰 요약이 "비슷하다/구별 어렵다"고 서술 |
| ③ | 두 사진이 서로 다른 유형을 지목해 하나로 정할 수 없다 | 사진별 `의심 유형`이 상충 |
| ④ | "무너지나요/안전한가요"만 묻는다 | 안전성 판정은 구조해석 영역 |

### 6-2. `null`이 **아닌** 경우 (오보류 방지)

| 상황 | 처리 |
|---|---|
| 사진 1장뿐 | 점수 산출(관통·대면 비교만 불가) |
| 사진 근거 없이 **메모만** 있음 | 점수 산출하되 **상한 55**, `recommended_action`은 `inspection` 이상, `unknowns` 1줄 |
| 사용자가 직접 잰 값을 밝힘 | 점수 산출(표의 "사용자가 직접 재서 폭을 수치로 밝힘" 행) |
| 유형 2개 이상 | 유형별로 골라 **높은 점수** + 가장 강한 action |
| 탐지 신뢰도가 40% 미만뿐 | 그 항목을 **신호로 세지 않는다**. 남는 신호가 없으면 결과적으로 ①과 같아진다 |

### 6-3. `null`일 때의 응답 형태 (서버가 추가로 강제하는 것 표시)

```json
{
  "observations": "사진 2장 모두에서 확인된 흔적이 없습니다.",
  "suspected_types": [],
  "severity_score": null,
  "reason": "판독 가능한 사진이 없고 메모에 확인 가능한 진술도 없어 단계를 정하지 않았습니다.",
  "causes": [],
  "recommended_action": "inspection",
  "care_steps": ["같은 자리를 밝은 곳에서 근접 촬영해 다시 진단해 주세요."],
  "supplies": [],
  "prevention_tips": [],
  "unknowns": ["확인 필요: 근접 사진. 사진이 있으면 유형과 단계를 다시 판단할 수 있습니다."],

  "work_type_name": "원인 점검",

```

| 서버가 추가로 하는 일 | 근거 |
|---|---|

## 7. 프롬프트에 넣지 말아야 할 것

| 금지 | 이유 | 대신 쓸 표현 |
|---|---|---|
| **계측값 추정** — 균열폭(mm), 절대면적(㎡), 함수율(%), CFU/㎥, TDR, 부착강도(MPa) | 사진에는 이 값을 만들 근거가 없다. 넣으면 `reason`에 "약 0.3mm 폭"처럼 **측정값 행세**를 한다 | "폭은 재지 않았습니다", "면적은 화면 기준입니다", "공기 중 농도는 확인되지 않았습니다" |
| **기준 수치·조문·표준번호** — 0.3mm, 20%, 0.392MPa, 0.93㎡, ISO 4628, ASTM D3359, 하자판정기준 제7조 | 숫자를 주면 그 숫자가 출력으로 돌아온다. 조문은 "단정 금지"와 정면 충돌한다 | "철근 노출 가능성", "폭 기준은 현장 측정값입니다" |

| **금액·일정·업체명 생성** — "보수비 30만원", "2일 소요" | 우리가 가진 정보가 아니다. 임차인-임대인 분쟁에서 근거로 오용된다 | "업체 견적이 필요합니다" |
| **관통·안전성 판정** — "관통균열입니다", "구조적으로 안전합니다" | 정면/배면 대조·구조해석이 필요하다. 입력에 없다 | "반대면 상태는 확인되지 않았습니다" |

| **임의 유형 라벨** — "표면 이상", "오염" | 서버가 조용히 걸러내 점수만 남는 모순 응답이 된다 | 공식 3종 또는 `[]` |


| 2 | **결정성이 보장되지 않는다** | `llm.py:113`의 `temperature: 0.2`, `seed` 미전송. 코드 변경이 필요해 이번 범위 밖이다. 표 선택으로 분산은 줄었지만 0은 아니다 |

### 9-2. 후속 검증 계획 (3개)

| # | 과제 | 방법 | 통과 기준 |
|---|---|---|---|
| 1 | **일치도 측정** | 동일 기록 20건을 2회 독립 생성해 밴드 일치율 계산 | 3밴드 Cohen's kappa **≥ 0.61**(상당) [LandisKoch]. 미달이면 표 행을 줄인다 |
