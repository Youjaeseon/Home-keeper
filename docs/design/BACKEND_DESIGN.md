# MVP 백엔드 설계

## 문서 범위

이 문서는 2026년 11월 20일 팀 회의 변경 사항을 반영한 MVP 전체의 백엔드 처리 규칙을 설명한다. 현재 저장소에 구현된 기능은 인증, 하자 기록 CRUD(`material` 포함), 사진·위치·재질 기반 **샘플 일괄 분석**, 그리고 **현재 MVP 흐름에서는 사용하지 않는 레거시/보류 상태의 대화·시연용 다음 질문 API**(`messages`, `next-question`)다. 회원 프로필, 소식지, 실제 모델 기반 사진 분석·진단, 내 기록 목록, 요청문 생성, 업체 검색과 1:1 채팅은 후속 구현 대상이다.

실행과 검증 절차는 [README](../../README.md), 테이블과 제약은 [DB 설계](DB_DESIGN.md), 앱 연동 계약은 [API 설계](API_DESIGN.md)를 따른다.

## 인증과 접근 권한

Expo 앱은 Supabase Auth(이메일·비밀번호)로 회원가입·로그인한다. 일반 회원가입은 `요청인`(`role='requester'`) 전용이며 닉네임, 거주 지역, 선택 등록 주소, 거주 형태를 인증된 사용자의 프로필로 저장한다. 시연용 `업체`(`role='provider'`) 계정은 사전에 등록해 업체 정보와 연결한다.

앱은 프로필, 소식지, 하자 기록, 업체 검색, 채팅을 FastAPI에 요청한다. FastAPI는 요청의 액세스 토큰을 검증하고, 기록의 조회·수정·분석·초안 생성에서는 검증된 사용자와 기록 소유자가 일치하는지 확인하며, 채팅에서는 참여자(요청인 또는 연결된 업체 계정) 여부를 확인한다.

## 회원 프로필과 등록 주소 (구현 예정)

회원가입 과정에서 `닉네임`, `거주 지역`, `등록 주소`(선택 입력), `거주 형태`(`월세`, `전세`, `반전세`, `자가`, `기타`)를 등록한다. `거주 지역`은 소식지 기본 노출과 업체 검색에 쓸 지역 ID와 연결하고, `등록 주소`는 주택을 식별하는 선택 문구로 저장한다. 집 안에서 하자가 생긴 위치는 하자 기록의 `location`으로 별도 관리한다. *(상세 등록 주소를 계속 유지할지 거주 지역만 수집할지는 팀 추가 논의 항목으로 둔다.)*

주소·지역이 필요한 단계(임대인 점검 요청문, 업체 찾기)에서는 현재 등록 주소와 거주 지역을 먼저 보여주고 맞는지 확인한다. 다르면 수정·저장 후 사용한다. 프로필이 없는 기존 계정은 프로필 등록으로 이어간다. Supabase 계정 생성 후 프로필 저장에 실패하면 같은 계정으로 프로필 저장을 재시도하며 새 계정을 중복 생성하지 않는다.

소식지와 업체 검색은 확인한 거주 지역 ID를 사용한다. 상세 `등록 주소`는 질문·진단·요청문 생성용 LLM 입력에서 제외한다. 주소가 들어갈 임대인 점검 요청문은 주소를 제외한 초안을 생성한 뒤 앱에서 확인한 주소를 반영한다. 주소를 수정한 요청문도 사용자 편집본과 같은 방식으로 현재 화면에서 유지한다. 거주 형태가 `자가`인 요청인의 결과 화면에서는 임대인 점검 요청문을 기본 숨긴다.

FastAPI는 자신의 프로필만 조회·저장하도록 토큰의 사용자 ID로 접근을 제한한다. 프로필 변경은 하자 입력 버전(`input_revision`)과 구분하며, 기존 기록이나 요청문을 자동으로 새 주소로 바꾸지 않는다. 실제 주소의 외부 DB 보관과 보유기간은 개인정보 검토의 미결정 사항으로 남긴다.

## 하자 기록의 생성과 저장

사용자가 새 하자 기록을 시작하면 FastAPI가 기록 ID를 발급한다. 분석 페이지에서는 AI 채팅창을 없애고 한 화면에서 같은 하자의 **사진 1~2장**(전체·근접, 1장 필수·2장째 선택), **위치**, **재질**, **선택 증상 메모**를 함께 입력받아 처리한다. `내 정보` 페이지의 **내 하자 분석 기록 목록**을 위해 `GET /records`로 본인 기록 목록(최신 수정순)을 조회해 과거 분석 결과 페이지를 다시 열 수 있게 한다.

사진 분석에서는 관찰한 흔적, 의심 유형(`크랙`, `벗겨짐`, `곰팡이`), 대략적인 위치 요약만 DB에 저장한다. 원본 사진과 화면 표시 좌표는 현재 분석 및 결과 화면에서만 사용하며 DB·서버 로그에 영구 저장하지 않는다.

## DB 접근과 저장 단위

앱 데이터 테이블은 Supabase Data API에 공개하지 않는다. FastAPI는 필요한 권한만 부여한 DB 계정으로 연결한다. 하자 기록과 채팅방은 토큰으로 검증한 사용자 ID를 함께 확인해 접근한다.

| 저장 단위 | 상태 | 저장할 값 |
| --- | --- | --- |
| 회원 프로필 (`profiles`) | 구현 예정 | 사용자 ID, 닉네임, 역할(`requester`/`provider`), 거주 지역 ID, 선택 등록 주소, 거주 형태(`monthly_rent`/`jeonse`/`semi_jeonse`/`owned`/`other`), 수정 시각. 로그인한 사용자 본인만 조회·수정한다. |
| 하자 기록 (`records`) | 구현됨 (`material` 추가 예정) | 기록 ID, 소유자 ID, 위치·재질·선택 증상 메모, 사진 관찰 요약, 최신 진단(JSONB), 최신 점검 요청문, 최신 견적 요청문 |
| 소식지 지원 사업 (`support_programs`) | 구현 예정 | 지원 사업 ID, 외부 ID, 출처(`gov24_api`/`seed`), 제목, 요약, 소관기관, 지역 구분(`national`/`local`), 지역 ID, 대상 거주 형태, 신청기한 원문·마감일, 신청방법, 원문 URL, 출처 표기 |
| 업체 (`providers` 등) | 테이블 구현됨 (`account_user_id` 추가 예정) | 업체 ID, 업체명, 연락처, 사전 등록 업체 계정 사용자 ID, 출장 지역 연결, 작업 종류 연결 |
| 채팅방·메시지 (`chat_rooms`, `chat_messages`) | 구현 예정 | 채팅방 ID, 요청인 ID, 업체 ID, 최근 연결 기록 ID, 발신자 ID·역할, 메시지 유형(`text`/`record_summary`), 연결 기록 ID, 본문·요약 페이로드, `client_message_id` |
| 질문·대화 메시지 (`questions`, `messages`) | 기존 구현 (MVP 미사용/보류) | 분석 채팅창 제거에 따라 현재 MVP에서는 호출하지 않는 레거시 테이블. 추후 설문/객관식 추가 질문 도입 시 재검토한다. |

업체 검색은 사용자가 확인한 거주 지역 `region_id`와 `work_type_id`를 받는다. FastAPI는 진단 시 AI에 등록된 작업 목록을 제공하고 그중 하나를 고르게 한다. 등록되지 않은 작업을 반환하거나 판단 근거가 부족하면 `원인 점검`을 선택하고 추천 이유를 보여준다. 앱은 같은 목록에서 제안된 작업을 미리 선택하며 사용자가 변경할 수 있다. 업체 검색이 성공했고 입력한 동네(시연 지역: 용인)와 작업이 모두 맞는 실제 업체가 없을 때만 API가 샘플 후보를 반환한다. 샘플 여부를 응답에 명시해 앱이 샘플 표시와 연락 시연 안내에 사용하게 한다.

## 일괄 분석과 진단 처리 (샘플 구현 완료)

사용자가 사진 1~2장과 위치·재질·선택 증상 메모를 입력하고 `분석하기`를 누르면, 앱은 `POST /records/{record_id}/analyze`로 한 번에 전송한다. 현재 구현은 실제 YOLO·비전 LLM·텍스트 LLM을 호출하지 않고 다음 순서로 샘플 결과를 저장한다.

1. **입력·파일 검증**: 기록 소유권을 먼저 확인하고, 사진 1~2장, JPEG/PNG/HEIC/HEIF, 한 장당 10MB 이하, `photo_roles`의 사진 수·허용값·중복 여부를 검증한다. 파일은 magic byte로 확인하며 실제 모델에는 전달하지 않는다.
2. **입력 스냅샷과 샘플 생성**: 현재 `input_revision`을 읽은 뒤 기록 행 잠금을 해제하고, 위치·재질·증상으로 결정적 샘플 분석을 만든다. 사진 bytes는 결과 생성에 사용하지 않는다.
3. **최종 저장**: 저장 직전에 기록 행을 다시 잠가 `input_revision`이 바뀌지 않았는지 확인한다. 바뀌었으면 아무것도 저장하지 않고 `409`를 반환한다. 제출한 위치·재질·증상이 기존 값과 다르면 `input_revision`을 1 올리고, `photo_observations`(샘플 상태), `diagnosis`, `diagnosis_revision`, `diagnosis_generation`을 같은 트랜잭션에 저장한다. 같은 입력이면 버전은 유지하고 생성 번호만 올린다.
4. **샘플 표시와 정리**: 응답과 진단의 `source="sample"`, `photo_analysis.applied=false`, `photos[].status="not_analyzed"`, `detections=[]`로 실제 사진 분석이 아님을 표시한다. 업로드 파일은 성공·실패 모두 닫고 원본 사진·좌표·신뢰도를 저장하거나 로그에 남기지 않는다.

실제 모델 연동 시 2단계에서 YOLO·비전 LLM·텍스트 LLM을 호출하고, 실패·미탐지 시 입력값만으로 진단을 이어가는 기존 폴백 규칙을 적용한다. 호출하는 동안 DB 행 잠금을 유지하지 않고, 저장 직전 재확인하는 구조를 그대로 사용한다.

위치·재질·증상이 나중에 `PATCH /records/{record_id}`로 바뀌면 기존 진단과 요청문을 이전 입력으로 만든 결과(`is_current=false`)로 표시하고 기존 요청문 복사를 막는다.

## 진단 응답과 저장

하자 기록의 `diagnosis` JSONB 컬럼에 최신 진단을 저장한다. 서버는 응답 구조와 허용된 값을 검증한 뒤 저장한다. 소유자 ID, 입력 버전, 진단 생성에 사용한 입력 버전과 생성 번호는 별도 컬럼으로 관리한다.

| 응답 필드 | 내용 |
| --- | --- |
| `observations` | 사진과 입력(위치·재질·증상)에서 확인한 흔적 요약과 사진 분석 반영 여부 |
| `severity_score` | `0`~`100` 정수(심각도 퍼센트). 정보가 부족하면 `null`로 두고 판단 보류로 처리한다. |
| `severity_level` | `low`(`0~39%`), `medium`(`40~69%`), `high`(`70~100%`), `undetermined`(판단 보류) |
| `reason` | 심각도(%)와 권장 대응의 산정 근거 |
| `causes` | 가능한 추정 원인 목록 (단정 표현 금지) |
| `estimation_notice` | AI 추정 안내 문구 (예: "사진과 입력 정보를 바탕으로 한 AI 추정이며, 정확한 원인은 현장 점검이 필요합니다.") |
| `recommended_action` | `self_care`(직접 조치), `inspection`(임대인 점검 요청), `provider_consult`(업체 상담) |
| `care_steps` | 해결방안에 표시할 단계별 처리 방법 |
| `supplies` | 해결방안에 함께 표시할 필요한 준비물 |
| `prevention_tips` | 재발 방지책 목록 |
| `unknowns` | 사진과 입력만으로 확인되지 않은 정보 (예: 내부 누수 여부, 재발 기간) |
| `work_type_id` | 등록된 작업 목록 중 업체 검색에 쓸 작업 ID. 샘플 모드에서 작업 데이터가 없으면 `null`일 수 있다. |
| `work_type_reason` | 해당 작업을 추천한 이유 |
| `source` | 결과 출처. 현재 샘플 구현은 항상 `sample`이다. |

정보가 부족하면 `severity_score`는 `null`, `severity_level`은 `undetermined`(`판단 보류`)로 표시한다. `추정 원인`에는 `causes`와 함께 `estimation_notice` 및 `unknowns`를 표시해 AI 오류·불확실성 대응 기준을 충족한다. `해결방안`에는 `recommended_action`, `care_steps`, `supplies`를 통합해 보여주고, `재발 방지책`에는 `prevention_tips`를 표시한다.

## 소식지 (주거 지원 사업, 구현 예정)

소식지 페이지에서는 주거 관련 중앙부처·지자체 지원 사업을 제공한다.

- **데이터 수급과 동기화**: 1차 소스는 공공데이터포털 `행정안전부_대한민국 공공서비스(혜택) 정보`(보조금24) Open API(`GET https://api.odcloud.kr/api/gov24/v3/serviceList`, 개발계정 자동승인·무료·일 10,000회)다. 백엔드에서 주거 관련 분류·키워드로 필터링해 `support_programs` 테이블에 동기화·캐싱한다.
- **시드 폴백**: API 키 미설정·지연·장애나 지자체 공고 누락에 대비해 검증된 실제 공고(전국 + 경기도·용인시 등)를 DB 시드(`source='seed'`)로 함께 둔다.
- **노출·필터링**: 기본 조회 시 로그인 사용자의 `거주 지역`과 일치하는 지자체 공고(`region_scope='local'`)와 `전국` 공고(`region_scope='national'`)를 함께 반환한다. `status=all|active` 필터를 제공하고, 사용자의 `거주 형태`와 일치하는 사업은 우선 정렬·태그 표시 대상으로 구분한다.
- **마감 판단과 정렬**: 보조금24 API의 `신청기한`은 `"상시신청"`, `"매년 하반기 접수"`, `"2026.10.31까지"` 같은 자유 텍스트다. 따라서 원문 `deadline_text`와 파싱·시드된 마감일 `deadline_date`(nullable `date`)를 함께 저장한다. `deadline_date`가 오늘 이전인 공고만 `is_closed=true`로 판정해 앱에서 `마감` 배지와 흐림 처리로 보여주고 목록 하단으로 정렬한다(`상시신청` 또는 날짜 미확정은 진행중 유지). 마감 공고도 클릭해 상세 요약을 열람할 수 있다.
- **상세 요약과 출처 표기**: 상세 조회에는 지원대상·내용·신청기한·신청방법·원문 URL(`detail_url`)·출처(`source_attribution`, 행정안전부·공공데이터포털 및 공공누리 조건)를 포함한다.

## 업체–요청인 1:1 채팅 (구현 예정)

기존 `SMS 메시지 보내기`를 앱 내 1:1 채팅으로 대체한다.

- **방 생성과 재사용**: 요청인이 업체 목록에서 실제 업체의 `채팅하기`를 누르면 `POST /chat/rooms`가 `(requester_id, provider_id)` 기준으로 기존 채팅방을 재사용하거나 새 방을 만든다. `샘플` 업체는 방을 만들지 않고 앱에서 시연 안내를 띄운다.
- **하자 분석 요약 자동 공유**: 분석 결과 화면을 거쳐 `record_id`와 함께 채팅방에 진입하면, 해당 하자 기록의 요약(의심 유형·위치·재질·심각도%·추정 원인)을 `message_type='record_summary'` 메시지로 채팅방에 자동 등록한다. 같은 기록 요약이 직전과 동일하면 중복 등록하지 않는다. 견적 요청문은 요청인이 채팅 입력창 초안으로 불러와 수정·전송하거나 복사해 쓸 수 있다.
- **접근 제어**: 채팅방·메시지 조회와 전송은 `room.requester_id == current_user_id` 또는 해당 업체의 `provider.account_user_id == current_user_id`인 참여자에게만 허용하고 그 외에는 404를 반환한다.
- **메시지 멱등성**: REST 메시지 전송(`POST /chat/rooms/{room_id}/messages`)은 `(room_id, client_message_id)` 유일 제약으로 재전송 중복을 막는다.
- **실시간 전송 방식(팀원 협의 보류)**: 메시지 저장·이력 조회는 FastAPI REST API로 두되, 실시간 수신 방식(`FastAPI REST 짧은 주기 폴링` vs `FastAPI WebSocket` vs `Supabase Realtime`)과 시연용 업체 계정 로그인 후 최소 화면 구성은 모바일·팀원과 협의해 확정한다. *(참고: 만약 `Supabase Realtime`을 채택할 경우, 기존 [003_backend_rls.sql](../../apps/api/migrations/003_backend_rls.sql)의 Data API 전면 차단 정책에서 채팅 테이블만 예외 RLS를 열어야 하는 보안 경계 변경이 필요하다.)*

## 개인정보 저장 검토

2026년 11월 19일 확인한 법령상 개인정보의 DB 저장 자체가 일률적으로 금지되는 것은 아니다. 동의 등 적법한 수집·이용 근거와 목적에 필요한 최소 수집, 보유기간·파기, 안전조치를 갖춰야 한다. 동의를 근거로 수집할 경우 목적, 항목, 보유·이용기간, 동의 거부 권리와 불이익을 안내한다. [개인정보 보호법 제15조](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1034516315), [제16조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1006184211), [제21조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335625)

해외 DB 보관이나 외부 AI 전달은 저장 목적 외에 위탁·제공 및 국외 이전 조건을 검토해야 한다. 국외 보관에도 국외 이전 규정이 적용되며, 별도 동의 등 법이 정한 근거가 필요하다. [제28조의8](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953)

회원가입 시 닉네임, 이메일 ID, 거주 지역, 선택 등록 주소, 거주 형태를 수집·저장한다. 채팅·프로필·증상 메모의 수집 범위와 보유기간, 상세 `등록 주소` 유지 여부, 외부 DB 보관 조건은 추가 확인이 필요하다. 요청문 수정본의 현재 화면 보관은 앞서 합의한 제품 범위다.

2026년 11월 19일 공식 해커톤 페이지와 첨부3(2026년 11월 3일 배포) 제7조, 제9조를 직접 확인했다. 공식 페이지는 개인정보 처리 시 관련 법령과 이용 조건 준수를 요구한다. 첨부3 제7조는 적법한 수집·이용 근거를 요구하며, 실제 개인정보가 불필요하면 가상·샘플 데이터를 사용하도록 한다. 제9조에도 개인정보 수집·이용의 적법한 근거 확보를 확인하는 항목이 있다.

DB 저장을 직접 허용한다는 별도 문구는 확인되지 않았으나, 개인정보 수집·이용을 조건부로 전제하므로 DB 저장 자체를 일괄 금지한 규정으로 읽히지는 않는다. 이는 확인한 규정에 대한 해석이다. 외부 AI 서비스(API 포함)로 실제 개인정보·민감정보를 보내는 행위는 동의 여부와 관계없이 명시적으로 금지한다. 제7조에는 외부 서비스에는 가상 데이터 또는 개인을 알아볼 수 없도록 처리한 데이터만 사용한다는 문장도 있어, 외부 SaaS DB에 실제 개인정보를 보관할 수 있다고 단정하지 않는다. Supabase를 포함한 외부 DB 서비스의 실제 개인정보 보관 허용 범위는 운영사무국 확인이 필요하다. [공식 해커톤 안내](https://korcham-careerfair.com/hackathon), [첨부3 제7조·제9조](https://drive.google.com/file/d/1PPCIMds1RBXces430OeGF2D7mQWkrdyj/view)

## 구현 메모

- 액세스 토큰은 PyJWT로 서명과 `exp`, `iat`, `iss`, `aud`, `sub`를 검증한다. HS256은 `SUPABASE_JWT_SECRET`, `RS256`·`ES256`은 `SUPABASE_URL/auth/v1/.well-known/jwks.json`을 사용한다. `sub`가 아니면 거부하고, 요청 본문의 `owner_id`는 받지 않는다.
- 요청마다 연결과 트랜잭션을 열고, 기록을 바꾸는 요청은 `records` 행을 `FOR UPDATE`로 잠근다. 조회는 `REPEATABLE READ`로 일관된 스냅샷을 읽는다.
- 테스트는 실제 PostgreSQL과 HS256 테스트 토큰을 사용하며, 인증 경계는 FastAPI 의존성 오버라이드로 대체할 수 있다. 운영 코드에는 인증 우회 분기가 없다.
- 요청 본문·비밀번호·토큰은 로그에 남기지 않는다. 처리하지 못한 예외는 트레이스백만 남기고 500을 반환한다.

## 요청문 편집

사용자가 수정한 요청문은 앱의 현재 화면에서만 유지한다. 수정본을 저장하는 API는 두지 않고 Supabase, 서버 로그, 앱의 영구 저장소에 남기지 않는다. 임대인 연락이나 업체 채팅 입력창에 붙여 넣을 때는 화면의 수정본을 사용한다. DB에는 마지막 생성 요청문을 저장한다. 회원 프로필에 저장한 등록 주소와 요청문 편집본은 별도로 관리한다. 등록 주소는 본인 프로필에서 조회하고, 주소가 필요하면 사용자 확인 후 앱에서 문구에 반영한다. 주소가 포함된 요청문 편집본은 서버로 다시 저장하지 않는다.

## 기존 구현 · MVP 미사용(보류): AI 추가 질문 대화

아래 규칙은 현재 코드(`apps/api/app/records.py`, `apps/api/app/sample_questions.py`)에 구현·테스트되어 있으나, 2026년 11월 20일 분석 페이지 채팅창 제거 결정에 따라 현재 MVP 화면에서는 호출하지 않는다. 추후 설문/객관식 추가 질문을 도입하기로 결정할 때 참고·재사용한다.

- **구현된 엔드포인트**: `POST /records/{record_id}/messages`, `PUT /records/{record_id}/messages/{message_id}`, `POST /records/{record_id}/next-question`
- **질문·메시지 저장 규칙**: `records.conversation_sequence`에서 공용 순번을 발급하고, `(record_id, client_message_id)` 유일 제약으로 재전송 멱등성을 보장한다. 과거 사용자 메시지를 `PUT`으로 수정하면 이후 대화·질문을 같은 트랜잭션에서 삭제하고 `input_revision`을 올린다.
- **시연용 다음 질문**: 실제 LLM 대신 `apps/api/app/sample_questions.py`가 창가 얼룩 사례의 2개 질문(`recurred`/`wiped` 등)을 `source="sample"`로 반환하고 `next_question_result`에 캐시한다.

## 일괄 분석 결과 분기와 검증 사례

사진 선택·위치·재질 입력 화면에서 한 장 또는 두 장을 고르고 위치·재질을 입력한 뒤 `분석하기`를 누르면 한 요청에 함께 전송한다. 현재 샘플 구현은 사진을 실제로 분석하지 않으므로 모든 사진이 `not_analyzed`이고 `photo_analysis.applied=false`다. 입력값 기반 진단은 생성한다.

- 실제 모델 연동 후 사진 두 장 중 한 장에서만 사용 가능한 결과를 얻어도 그 관찰 결과와 위치·재질로 진단을 생성하고, 실패한 사진의 상태를 별도로 표시한다.
- 실제 모델 연동 후 업로드한 사진 모두에서 의심 영역을 찾지 못하거나 사진 분석이 실패·거절되어도, 이미 입력한 **위치·재질·증상만으로** 진단을 생성한다(`photo_analysis_applied=false`).
- 같은 입력에서 진단 재생성에 성공하면 이전 요청문 복사가 차단되고 현재 진단으로 새 요청문을 만든다. 진단 재생성 실패 시 기존 유효 결과는 유지된다.
- 요청문 생성 도중 진단이 교체되면 늦게 온 이전 요청문을 저장하지 않고 `409 Conflict`를 반환한다.

## 이미지 분석 연동 (실제 모델 연동 시)

이미지 인식 담당자는 사진을 받아 YOLO 탐지 결과(`크랙`, `벗겨짐`, `곰팡이`)를 반환하는 별도 API를 제공한다. 현재 샘플 구현은 이 API를 호출하지 않는다. 연동 시 앱은 FastAPI에 사진과 위치·재질을 보내고, FastAPI가 YOLO API를 호출한다. 필요한 경우 FastAPI가 비전 LLM으로 2차 분석을 요청한다. YOLO와 앱용 백엔드는 각각의 실행 환경에서 운영한다. YOLO API의 요청·응답과 인증 방식, 제한 시간은 이미지 담당자와 맞춘다.

임시 응답 계약은 사진별 분석 상태와 탐지 후보 목록이다. 각 후보에는 유형, 신뢰도, 사각형 좌표를 담고 사진의 너비·높이를 함께 반환한다. 한 사진에서 여러 후보를 반환할 수 있다. 픽셀 단위 영역 마스크는 모델이 제공할 때 추가한다. 탐지 결과가 없는 성공 응답과 분석 실패를 구분한다. 구체적인 좌표 형식과 신뢰도 기준은 이미지 담당자 확인 전이다.

## 진단과 요청문의 재사용

진단은 같은 입력 버전의 결과를 재사용한다. 요청문은 입력 버전과 생성에 사용한 진단 생성 번호가 모두 현재 값과 일치할 때만 재사용하고 복사할 수 있다. 앱이 화면을 다시 열거나 통신 문제로 같은 요청을 보내도 저장된 최신 결과를 재사용한다.

사용자가 `다시 생성`을 선택하면 생성 API에 `regenerate=true`를 보내 모델을 새로 호출한다. 새 결과가 검증과 입력 버전 검사를 통과했을 때만 최신본을 교체한다. 실패하면 기존 값을 유지한다. 진단 저장 성공 시마다 `diagnosis_generation`을 증가시킨다. 진단 재생성 성공 시 이전 생성 번호의 요청문은 이전 결과로 표시하고 복사를 막는다.

요청문은 생성 시작 시의 입력 버전과 진단 생성 번호를 함께 기록한다. 저장 직전에 기록 행을 잠근 트랜잭션에서 두 값이 현재 값과 일치하는지 확인한다. 생성 중 진단이 교체됐으면 이전 진단에 따른 요청문을 저장하지 않고 `409 Conflict`를 반환한다. 재생성에 실패한 진단은 생성 번호와 기존 요청문의 유효성을 바꾸지 않는다.

## 모델 호출

일괄 분석(사진 분석 + 진단 생성), 진단 재생성, 요청문 생성은 각각 한 번의 요청과 응답으로 처리한다. 앱은 요청 중 진행 상태를 표시한다. 사진 분석이 제한 시간 초과나 호출 실패로 끝나도 입력한 위치·재질·증상만으로 진단을 이어간다. 진단 생성 자체가 실패하면 입력(위치·재질·증상)을 유지하고 `진단을 완료하지 못했어요`와 `다시 시도`를 표시한다. 정보 부족으로 판단한 `판단 보류`(`severity_score=null`)와 진단 생성 실패를 구분한다. 요청문 생성이 실패하면 앱은 `다시 생성`과 모델 호출 없는 `기본 양식 보기`를 함께 제공한다.

상세 제품 흐름과 검증 기준은 [프로젝트 계획](../plans/PROJECT_PLAN.md)에 있다.
