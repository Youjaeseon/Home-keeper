# MVP 백엔드 설계

## 문서 범위

이 문서는 합의한 MVP 전체의 백엔드 처리 규칙을 설명한다. 현재 구현은 인증, 하자 기록과 사용자 메시지 저장·조회·수정이다. 사진 분석과 생성·검색 API는 후속 구현 대상이다.

실행과 검증 절차는 [README](../../README.md), 테이블과 제약은 [DB 설계](DB_DESIGN.md), 앱 연동 계약은 [API 설계](API_DESIGN.md)를 따른다.

## 인증과 접근 권한

Expo 앱은 팀이 준비한 이메일·비밀번호 계정으로 Supabase Auth에 로그인한다. 앱은 하자 기록과 업체 검색을 FastAPI에 요청한다. FastAPI는 요청의 액세스 토큰을 검증하고, 하자 기록의 조회·수정·요청문 생성에서 검증된 사용자와 기록 소유자가 일치하는지 확인한다.

## 하자 기록의 생성과 저장

사용자가 새 하자 기록을 시작하면 FastAPI가 기록 ID를 발급한다. 분석 실패 후 직접 입력으로 전환해도 같은 ID를 사용한다. 위치, 증상, 추가 답변, 진단 결과, 점검 요청문과 견적 요청문은 Supabase에 저장한다. 같은 하자의 전체 사진과 근접 사진을 최대 두 장 받는다. 사진 한 장으로 분석과 질문을 시작할 수 있고, 두 번째 사진은 선택으로 받는다. 부족한 정보는 채팅 질문으로 확인한다. 전체 사진은 위치와 퍼진 범위를, 근접 사진은 표면의 흔적을 확인하는 데 사용한다. 실제 면적 측정은 기준물 촬영 또는 깊이 측정을 검증한 뒤 도입할 후속 후보로 둔다. 사진 분석에서는 관찰한 흔적, 의심 유형, 대략적인 위치만 저장한다. 원본 사진과 화면 표시 좌표는 현재 분석 및 결과 화면에서만 사용한다. 다음 질문과 진단은 저장된 관찰 결과를 사용한다.

## DB 접근과 저장 단위

앱 데이터 테이블은 Supabase Data API에 공개하지 않는다. FastAPI는 필요한 권한만 부여한 DB 계정으로 연결한다. 하자 기록과 그에 딸린 질문·답변은 기록 ID와 토큰으로 검증한 사용자 ID를 함께 확인해 접근한다.

| 저장 단위 | 저장할 값 |
| --- | --- |
| 하자 기록 | 기록 ID, 소유자 ID, 위치·증상, 최신 진단(JSONB), 최신 점검 요청문, 최신 견적 요청문 |
| 질문 | 질문 ID, 하자 기록 ID, 생성 순서, 질문 내용, 선택지, 필요한 정보의 확인 여부. 질문 하나당 한 행으로 저장한다. |
| 대화 메시지 | 메시지 ID, 하자 기록 ID, 사용자 메시지의 `client_message_id`, 연결된 질문 ID, 대화 순서, 발신자, 내용. 질문 하나에 여러 사용자 메시지와 AI 응답을 연결할 수 있다. |
| 업체 | 업체 ID, 업체명, 연락처 |
| 검색 지역과 작업 종류 | 팀이 준비한 선택 목록. 각 지역과 작업에 ID를 부여한다. 지역 표시에는 시·군·구를 함께 제공한다. |
| 업체 출장 지역 | 업체와 출장 가능 지역의 연결. 업체 한 곳에 여러 지역을 등록할 수 있다. |
| 업체 작업 종류 | 업체와 제공하는 작업 종류의 연결. 업체 한 곳에 여러 종류를 등록할 수 있다. |

답변 저장과 다음 질문 생성은 별도 API로 둔다. 앱은 질문 ID에 사용자 메시지를 먼저 저장한 뒤 AI 응답과 다음 질문을 요청한다. 질문 생성 실패 시 해당 호출만 재시도한다. 현재 정보로 결과 보기를 선택하면 서버에 저장된 입력으로 진단을 요청한다. 진단과 두 종류의 요청문은 각각 최신본을 저장하고, 생성에 실패하면 기존 값을 유지한다.

위치·증상 또는 답변이 바뀌면 기존 진단과 요청문을 이전 입력으로 만든 결과로 표시한다. 기존 요청문은 복사를 막고, 새 진단 후 현재 입력에 맞는 요청문을 새로 생성해 복사한다.

업체 검색은 `region_id`와 `work_type_id`를 받는다. FastAPI는 AI에 등록된 작업 목록을 제공하고 그중 하나를 고르게 한다. 등록되지 않은 작업을 반환하거나 판단 근거가 부족하면 `원인 점검`을 선택하고 추천 이유를 보여준다. 앱은 같은 목록에서 제안된 작업을 미리 선택하며 사용자가 변경할 수 있다. 업체 검색이 성공했고 입력한 동네와 작업이 모두 맞는 실제 업체가 없을 때만 API가 샘플 후보를 반환한다. 샘플 여부를 응답에 명시해 앱이 샘플 표시와 연락 버튼의 시연 안내에 사용하게 한다.

## 진단 응답과 저장

하자 기록의 `diagnosis` JSONB 컬럼에 최신 진단을 저장한다. 서버는 응답 구조와 허용된 값을 검증한 뒤 저장한다. 소유자 ID, 입력 버전, 진단 생성에 사용한 입력 버전은 별도 컬럼으로 관리한다.

| 응답 필드 | 내용 |
| --- | --- |
| `observations` | 사진과 답변에서 확인한 흔적과 위치 |
| `severity` | `low`, `medium`, `high`, `undetermined`. 앱에서 낮음, 중간, 높음, 판단 보류로 표시한다. |
| `reason` | 심각도와 권장 대응의 판단 이유 |
| `recommended_action` | `self_care` 또는 `inspection`. 직접 조치 또는 점검 요청으로 표시한다. |
| `care_steps` | 직접 조치를 권할 때의 처리 방법 |
| `supplies` | 직접 조치에 필요한 준비물 |
| `unknowns` | 확인되지 않은 정보 |
| `work_type_id` | 등록된 작업 목록 중 업체 검색에 쓸 작업 ID |
| `work_type_reason` | 해당 작업을 추천한 이유 |

정보가 부족하면 심각도는 `undetermined`로 표시한다. 재발했거나 원인이 불명확한 경우 권장 대응은 `inspection`으로 한다. 직접 조치 시 처리 방법과 준비물을 표시하고, 점검 요청 시 임대인 점검 요청문을 주 버튼으로 표시한다. 업체 찾기는 두 경우 모두 제공한다.

## 개인정보 저장 검토

2026년 11월 19일 확인한 법령상 개인정보의 DB 저장 자체가 일률적으로 금지되는 것은 아니다. 동의 등 적법한 수집·이용 근거와 목적에 필요한 최소 수집, 보유기간·파기, 안전조치를 갖춰야 한다. 동의를 근거로 수집할 경우 목적, 항목, 보유·이용기간, 동의 거부 권리와 불이익을 안내한다. [개인정보 보호법 제15조](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1034516315), [제16조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1006184211), [제21조](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335625)

해외 DB 보관이나 외부 AI 전달은 저장 목적 외에 위탁·제공 및 국외 이전 조건을 검토해야 한다. 국외 보관에도 국외 이전 규정이 적용되며, 별도 동의 등 법이 정한 근거가 필요하다. [제28조의8](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953)

저장 전 자동 마스킹은 설계 후보이며 법에서 모든 대화에 일률적으로 요구한 방식으로 취급하지 않는다. 채팅 개인정보의 수집 범위와 보유기간은 아직 결정 전이다. 요청문 수정본의 현재 화면 보관은 앞서 합의한 제품 범위다.

2026년 11월 19일 공식 해커톤 페이지와 첨부3(2026년 11월 3일 배포) 제7조, 제9조를 직접 확인했다. 공식 페이지는 개인정보 처리 시 관련 법령과 이용 조건 준수를 요구한다. 첨부3 제7조는 적법한 수집·이용 근거를 요구하며, 실제 개인정보가 불필요하면 가상·샘플 데이터를 사용하도록 한다. 제9조에도 개인정보 수집·이용의 적법한 근거 확보를 확인하는 항목이 있다.

DB 저장을 직접 허용한다는 별도 문구는 확인되지 않았으나, 개인정보 수집·이용을 조건부로 전제하므로 DB 저장 자체를 일괄 금지한 규정으로 읽히지는 않는다. 이는 확인한 규정에 대한 해석이다. 외부 AI 서비스(API 포함)로 실제 개인정보·민감정보를 보내는 행위는 동의 여부와 관계없이 명시적으로 금지한다. 제7조에는 외부 서비스에는 가상 데이터 또는 개인을 알아볼 수 없도록 처리한 데이터만 사용한다는 문장도 있어, 외부 SaaS DB에 실제 개인정보를 보관할 수 있다고 단정하지 않는다. Supabase를 포함한 외부 DB 서비스의 실제 개인정보 보관 허용 범위는 운영사무국 확인이 필요하다. [공식 해커톤 안내](https://korcham-careerfair.com/hackathon), [첨부3 제7조·제9조](https://drive.google.com/file/d/1PPCIMds1RBXces430OeGF2D7mQWkrdyj/view)

## 구현 메모

- 액세스 토큰은 PyJWT로 서명과 `exp`, `iat`, `iss`, `aud`, `sub`를 검증한다. HS256은 `SUPABASE_JWT_SECRET`, `RS256`·`ES256`은 `SUPABASE_URL/auth/v1/.well-known/jwks.json`을 사용한다. `sub`가 아니면 거부하고, 요청 본문의 `owner_id`는 받지 않는다.
- 요청마다 연결과 트랜잭션을 열고, 기록을 바꾸는 요청은 `records` 행을 `FOR UPDATE`로 잠근다. 조회는 `REPEATABLE READ`로 일관된 스냅샷을 읽는다.
- 메시지 재전송은 소유권 확인 뒤, 버전 검사 전에 기존 `client_message_id`를 찾는다. 이 순서로 최초 저장이 버전을 올린 뒤에도 같은 요청이 성공한다.
- 테스트는 실제 PostgreSQL과 HS256 테스트 토큰을 사용하며, 인증 경계는 FastAPI 의존성 오버라이드로 대체할 수 있다. 운영 코드에는 인증 우회 분기가 없다.
- 요청 본문·비밀번호·토큰은 로그에 남기지 않는다. 처리하지 못한 예외는 트레이스백만 남기고 500을 반환한다.

## 요청문 편집

사용자가 수정한 요청문은 앱의 현재 화면에서만 유지한다. 수정본을 저장하는 API는 두지 않고 Supabase, 서버 로그, 앱의 영구 저장소에 남기지 않는다. 전화·메시지 앱으로 보낼 때는 화면의 수정본을 사용한다. DB에는 마지막 생성 요청문을 저장한다. 사용자가 화면에서 덧붙인 주택 식별 정보 등은 수정본과 함께 취급한다.

## 질문과 사용자 확인

추가 질문과 답변은 채팅창 형태로 보여준다. 질문마다 텍스트 입력 또는 미리 제시한 선택지를 눌러 답할 수 있게 한다. 선택지는 단일 선택이며 누르면 바로 답변으로 저장하고 다음 질문을 요청한다. 선택한 문구를 사용자 메시지로 저장한다. 선택지는 질문 안에서 구분할 ID와 표시 문구를 갖는다. 앱은 선택 시 선택지 ID를 보내고, 서버는 그 질문에 제공한 선택지인지 확인한 뒤 서버에 저장된 문구로 메시지를 만든다. 직접 입력 시에는 입력한 문구를 저장한다. 서버는 질문 내용과 선택지를 반환한다. 화면 하단에 텍스트 입력창을 항상 제공하고, AI 질문 아래에 선택 버튼을 함께 보여준다. 사용자는 버튼을 누르거나 입력창에 답을 적고 전송할 수 있다. AI 응답을 기다리는 동안 입력창에 글을 쓸 수 있으나 전송 버튼과 선택 버튼은 비활성화한다. 응답 생성에 실패하면 저장된 사용자 메시지로 AI 응답만 재시도한다.

질문과 메시지는 기록 안에서 순서를 관리한다. 이전 사용자 메시지를 변경하면 그 메시지 뒤의 대화와 질문을 삭제하고 변경한 내용부터 다시 진행한다.

사용자가 질문과 직접 관련 없는 내용을 보내도 메시지를 저장한다. AI는 짧게 반응한 뒤 필요한 질문을 이어간다. 질문에 필요한 정보를 답하지 않았다면 해당 정보는 미확인으로 유지한다. 사용자 메시지가 있다는 사실만으로 질문을 응답 완료로 처리하지 않는다.

사진 분석 결과보다 사용자가 확인하거나 수정한 위치·증상을 다음 질문, 진단, 요청문의 기준으로 삼는다. 관찰 결과와 사용자 확인 내용은 구분해 저장한다.

## 입력 버전과 생성 재시도

하자 기록에 `input_revision`을 둔다. 사용자 메시지가 추가되거나 위치·증상·답변 또는 저장된 사진 관찰 내용이 실제로 바뀌면 변경 내용과 함께 같은 트랜잭션에서 버전을 올린다. 같은 값을 다시 저장해도 버전은 유지한다. 답변 저장 요청에는 앱이 편집을 시작할 때 확인한 `input_revision`을 함께 보낸다. 서버는 같은 트랜잭션에서 버전을 확인하고 답변 변경과 후속 질문·답변 삭제를 처리한다. 버전이 다르면 변경 없이 `409 Conflict`를 반환한다. 앱은 최신 기록을 보여주고 다시 확인받는다.

질문·진단·요청문은 생성에 사용한 입력 버전을 기록한다. 저장 시 현재 버전과 일치하는 경우에만 결과를 저장한다. 생성 도중 입력이 바뀌면 이전 결과를 저장하지 않고 `409 Conflict`를 반환한다. 앱은 최신 상태를 확인하고 다시 요청한다.

이미 답한 질문의 답변을 수정할 때 이후 질문·답변이 있으면 앱에서 먼저 경고한다. 경고 문구는 “이 답변을 바꾸면 이후 질문과 답변이 삭제되고, 변경한 답변을 기준으로 다시 진행해요.”로 한다. 버튼은 `취소`와 `답변 바꾸기`를 제공한다. 취소하면 저장 요청을 보내지 않는다. 변경을 확인한 뒤 답변 값이 실제로 달라졌다면 서버는 답변 저장, 수정한 메시지 뒤의 대화와 질문 삭제, 입력 버전 증가를 같은 트랜잭션에서 처리한다. 이후 질문과 진단은 남아 있는 입력을 바탕으로 생성한다.

다음 질문 요청 시 현재 입력 버전에 대해 이미 생성한 AI 응답과 질문이 있으면 그대로 반환한다. 새 사용자 메시지가 들어오면 해당 내용을 반영해 AI 응답을 생성하고, 미확인 정보가 있으면 필요한 질문을 이어간다. 동시에 요청해도 같은 버전의 미응답 질문은 하나만 저장한다. 추가 질문이 필요 없으면 `ready_for_diagnosis`를 반환한다. 완료 응답 전체를 `next_question_result`와 `next_question_revision`으로 기록에 저장한다. 질문과 짧은 응답이 모두 null인 종료 응답도 저장한다. 입력 버전이 같으면 이 저장 응답을 그대로 반환한다. 질문·AI 메시지·완료 응답은 입력 버전을 검사한 같은 트랜잭션에서 저장하며, 모델 호출에 실패하면 완료 응답을 기록하지 않는다.

## 메시지 중복 전송

앱은 새 사용자 메시지마다 `client_message_id`를 만들고 재전송할 때 같은 값을 사용한다. 서버는 기록 ID와 `client_message_id` 조합에 유일 제약을 둔다. 같은 요청이 다시 오면 저장한 메시지를 반환하고 입력 버전을 올리지 않는다. 기록 소유권을 확인한 뒤 기존 메시지 여부를 먼저 확인하므로, 최초 저장으로 입력 버전이 바뀌어도 동일 요청을 재전송할 수 있다. 같은 ID에 다른 내용을 보내면 `409 Conflict`로 거부한다.

## API 초안

아래 경로와 필드는 앱·백엔드 연동을 위한 초안이다. 기록을 다루는 모든 경로에서 로그인과 기록 소유권을 확인한다.

| 메서드와 경로 | 입력 | 성공 응답 |
| --- | --- | --- |
| `POST /records` | 없음 | `record_id`, `input_revision` |
| `GET /records/{record_id}` | 없음 | 저장된 입력, 질문·답변, 진단·요청문 및 각 결과의 입력 버전 |
| `PATCH /records/{record_id}` | 변경할 위치·증상 | 저장된 값, `input_revision` |
| `POST /records/{record_id}/photo-analysis` | 사진 한 장 또는 두 장과 각 사진의 역할(전체·근접), 외부 분석 동의 여부 | 분석 상태, 관찰 결과, 사진별 현재 화면용 표시 좌표 |
| `POST /records/{record_id}/messages` | `client_message_id`, 연결할 질문 ID, 직접 입력 문구 또는 선택지 ID, `input_revision` | 저장한 메시지, `input_revision` |
| `PUT /records/{record_id}/messages/{message_id}` | 수정할 내용, 편집 시작 시 확인한 `input_revision` | 저장한 메시지, `input_revision` |
| `POST /records/{record_id}/next-question` | 없음 | AI 응답과 질문 ID·내용·선택지 또는 `ready_for_diagnosis` |
| `POST /records/{record_id}/diagnosis` | 없음 | 심각도, 판단 이유, 권장 행동, 추천 작업 ID, 결과의 입력 버전 |
| `POST /records/{record_id}/drafts/{kind}` | 요청문 종류는 경로로 지정 | 요청문과 결과의 입력 버전 |
| `GET /records/{record_id}/drafts/{kind}/template` | 요청문 종류는 경로로 지정 | 현재 기록에서 확인한 사실을 채운 기본 양식과 입력 버전 |
| `GET /regions`, `GET /work-types` | 없음 | 검색에 사용하는 ID와 화면 표시 이름 |
| `GET /providers` | `region_id`, `work_type_id` | 업체 후보 목록과 샘플 여부 |

## 사진별 분석 결과

사진 선택 화면에서 한 장 또는 두 장을 고른 뒤 사용자가 `분석하기`를 누르면 선택한 사진을 한 요청에 함께 전송한다. FastAPI는 받은 사진들을 분석하고, 앱은 응답을 받은 뒤 채팅 화면으로 이어간다. 사용 가능한 결과가 없으면 직접 입력을 안내한다.

사진 두 장을 받은 경우 각 사진의 분석 상태를 구분한다. 한 장에서만 사용 가능한 결과를 얻어도 그 관찰 결과로 질문과 진단을 이어간다. 분석하지 못한 사진은 앱에 해당 상태를 표시하고, 부족한 정보는 채팅으로 확인한다. 사진 한 장을 받은 경우에도 같은 기준으로 처리한다. 업로드한 모든 사진에서 사용 가능한 결과가 없으면 위치·증상을 직접 입력하는 경로로 이어간다.

## 검증할 사례

- 사진 한 장에서 결과를 얻으면 두 번째 사진 없이 진행한다.
- 사진 두 장 중 한 장만 결과를 얻으면 성공한 관찰 결과를 사용하고 실패한 사진을 표시한다.
- 업로드한 사진 모두에서 결과를 얻지 못하면 직접 입력으로 진행한다.
- 같은 입력에서 진단 재생성에 성공하면 이전 요청문 복사가 차단되고 현재 진단으로 새 요청문을 만든다. 진단 재생성 실패 시 기존 유효 결과는 유지된다.
- 요청문 생성 도중 진단이 교체되면 늦게 온 이전 요청문을 저장하지 않고 충돌을 반환한다.
- 추가 질문과 짧은 AI 응답이 모두 없는 종료 응답이 유실된 뒤 재요청해도 모델을 재호출하지 않고 같은 종료 응답을 반환한다.

## 이미지 분석 연동

이미지 인식 담당자는 사진을 받아 YOLO 탐지 결과를 반환하는 별도 API를 제공한다. 앱은 FastAPI에 사진을 보내고, FastAPI가 YOLO API를 호출한다. 필요한 경우 FastAPI가 비전 LLM으로 2차 분석을 요청한다. YOLO와 앱용 백엔드는 각각의 실행 환경에서 운영한다. YOLO API의 요청·응답과 인증 방식, 제한 시간은 이미지 담당자와 맞춘다.

임시 응답 계약은 사진별 분석 상태와 탐지 후보 목록이다. 각 후보에는 유형, 신뢰도, 사각형 좌표를 담고 사진의 너비·높이를 함께 반환한다. 한 사진에서 여러 후보를 반환할 수 있다. 픽셀 단위 영역 마스크는 모델이 제공할 때 추가한다. 탐지 결과가 없는 성공 응답과 분석 실패를 구분한다. 구체적인 유형 목록, 좌표 형식, 신뢰도 기준은 이미지 담당자 확인 전이다.

## 진단과 요청문의 재사용

진단은 같은 입력 버전의 결과를 재사용한다. 요청문은 입력 버전과 생성에 사용한 진단 생성 번호가 모두 현재 값과 일치할 때만 재사용하고 복사할 수 있다. 앱이 화면을 다시 열거나 통신 문제로 같은 요청을 보내도 저장된 최신 결과를 재사용한다.

사용자가 `다시 생성`을 선택하면 생성 API에 `regenerate=true`를 보내 모델을 새로 호출한다. 새 결과가 검증과 입력 버전 검사를 통과했을 때만 최신본을 교체한다. 실패하면 기존 값을 유지한다. 진단 저장 성공 시마다 `diagnosis_generation`을 증가시킨다. 현재 입력에 대한 진단이 유효한지와 요청문이 현재 진단을 사용했는지를 함께 확인한다. 진단 재생성 성공 시 이전 생성 번호의 요청문은 이전 결과로 표시하고 복사를 막는다.

요청문은 생성 시작 시의 입력 버전과 진단 생성 번호를 함께 기록한다. 저장 직전에 기록 행을 잠근 트랜잭션에서 두 값이 현재 값과 일치하는지 확인한다. 생성 중 진단이 교체됐으면 이전 진단에 따른 요청문을 저장하지 않고 `409 Conflict`를 반환한다. 재생성에 실패한 진단은 생성 번호와 기존 요청문의 유효성을 바꾸지 않는다.

## 모델 호출

사진 분석, 다음 질문 생성, 진단 생성, 요청문 생성은 각각 한 번의 요청과 응답으로 처리한다. 앱은 요청 중 진행 상태를 표시한다. 제한 시간 초과나 호출 실패 시 사진 분석은 직접 입력으로 이어가고, 질문 생성은 재시도하거나 현재 정보로 결과를 볼 수 있다. 요청문 생성이 실패하면 앱은 `다시 생성`과 `기본 양식 보기`를 함께 제공한다. 다시 생성은 생성 API를 재호출하고, 기본 양식은 별도 API에서 현재 기록의 확인된 사실만 채워 가져온다. 기본 양식에는 모델을 호출하지 않으며, 사용자는 양식을 수정하고 복사할 수 있다. 진단 생성이 실패하면 입력과 대화를 유지하고 `진단을 완료하지 못했어요`와 `다시 진단하기`를 표시한다. 정보 부족으로 판단한 `판단 보류`와 진단 생성 실패를 구분한다. 이전 버전 진단은 최신 결과로 사용하지 않는다. 시연 환경에서 응답 시간이 자주 요청 제한을 넘으면 작업 상태를 별도로 조회하는 방식을 검토한다.
